# Windows 首版验收问题修复设计

> 实现状态更新（2026-07-28）：本文定义的修复已经完成并通过自动回归、静态分析
> 和 Windows Release 构建；完整人工复测仍待用户执行。当前状态见
> `docs/project-status.md`。

## 1. 背景与目标

Windows 首版已经完成第一轮人工验收，基础登录、教务与二课采集、本地导入、周日程、
Task、账号和设置页面均可运行，但验收暴露出以下未闭环问题：

- 重复同步后旧考试仍参与显示，形成重复重叠事件；
- “全部同步”没有正确处理两个来源各自的登录和恢复流程；
- 日程和 Task 缺少可用的详情入口，已有冲突、覆盖和 PlanBlock 能力无法从 UI 到达；
- Task 截止时间仍使用手工文本输入；
- 删除凭据后的重新认证语义不明确；
- 完全重置没有清除完整账号状态，也没有返回首次登录页面；
- 周课表空白区域创建事件的入口没有产品价值。

本次修复不扩展首版产品范围，也不引入 LLM、移动端采集或新的来源。目标是让已有
领域能力通过完整交互链路可用，并使同步、账号和完整快照的语义与既有契约一致。

## 2. 实现原则

1. 继续复用现有 repository、service、页面组件和 GoRouter，不另建平行实现。
2. 学校来源数据与用户覆盖分离。同步可以改变来源可见性，但不得删除
   `UserOverlay`。
3. 时间重叠、人工冲突关系和前景主事件是三个不同概念，不能相互自动推导。
4. 所有来源同步必须产生明确的逐来源结果，不能用部分成功冒充全部成功。
5. 删除安全凭据和删除本地业务数据是两个独立操作。
6. 修复按风险分组，以回归测试先行；真实学校页面仍只通过人工登录验收。

## 3. 数据与同步

### 3.1 完整快照中的缺失记录

`SourceBundle` 完整快照导入后，范围内未再次出现的来源记录继续标记为
`missing_within_scope`，不物理删除对应 `CalendarEvent`、`SourceRecord` 或
`UserOverlay`。

有效日程查询增加来源存在性条件：

- `source == user` 的个人事件不依赖 `SourceRecord`，照常显示；
- 学校来源事件仅在映射的 `SourceRecord.presence` 不是
  `missing_within_scope` 时显示；
- `outside_scope` 仍然保留并可显示，保证二课滚动窗口之外的历史记录不会仅因窗口
  移动消失；
- 明确取消、用户隐藏及其他既有状态继续遵循当前领域规则。

该规则解决同一考试外部身份发生变化后，新旧记录同时显示的问题，同时保留历史身份
和用户修改。

### 3.2 “全部同步”的顺序

“全部同步”严格按配置顺序执行教务和已报名二课日程。每个来源必须完成以下状态机后，
下一来源才能启动：

```text
start
  -> success | failed | needs_user_login
  -> needs_user_login: resume | cancel
  -> terminal result
  -> next source
```

手动同步在 `needs_user_login` 时等待用户完成或取消登录，再继续下一来源。启动时的
12 小时自动同步不主动弹出登录流程；它取消当前待登录采集、记录“需要重新登录”，
然后继续检查下一来源。这样不会让前一个 Bridge 浏览器任务占用后一个来源。

“全部同步”最终分别显示两个来源的结果。任何来源失败都不得将整体呈现为全部成功。

### 3.3 同步错误

同步层提供稳定、可区分的错误状态：

- `reauthentication_required`：本地账号存在但安全凭据已删除；
- `needs_user_login`：凭据存在，但网站会话需要用户完成登录或验证码；
- `account_mismatch`：学校页面身份与当前本地账号不一致；
- `bridge_busy`：已有采集任务尚未结束；
- `sync_failed`：不属于以上类别的明确采集或导入失败。

界面必须显示可执行的下一步。缺少凭据时直接引导重新登录，不启动一个必然失败的
采集任务。

## 4. 日程交互

### 4.1 点击与详情

周课表点击行为按可见事件数量区分：

- 单个事件：直接进入事件详情；
- 重叠事件：第一次点击打开独立的重叠事件列表，第二次选择具体事件进入详情；
- 已不存在的事件：返回日程页并提示“记录已不存在”。

详情页通过事件 ID 查询当前账号下的 `EffectiveEventRecord`，不把过期的完整记录
作为路由状态长期传递。详情展示标题、时间、地点、来源、状态、备注和适用的用户覆盖。

学校来源事件支持隐藏和编辑用户覆盖，不允许删除来源事实。个人事件支持编辑和删除。

### 4.2 用户覆盖

事件详情复用 `OverlayService`，提供当前模型已经支持的字段：

- 出勤层级；
- 听讲模式；
- 自由备注；
- 用户颜色；
- 隐藏状态；
- 前景优先级。

保存后周课表立即读取有效事件投影。来源再次同步不会覆盖这些字段。

### 4.3 重叠、冲突与前景主事件

重叠列表提供“处理冲突”入口，并复用 `ConflictEditor` 和 `ConflictService`。
用户可以：

- 将选定事件对标记为“冲突”或“不冲突”；
- 修改或删除已有人工冲突关系；
- 在重叠组中指定一个前景主事件。

前景主事件通过用户覆盖优先级表达，不改变冲突关系。渲染规则保持已确认设计：主事件
位于前景并轻微透明，其他事件在同一区域弱化显示；人工确认为冲突的事件显示右上角
红色圆圈感叹号。

隐藏学校事件、删除个人事件、调整冲突和前景主事件均写入操作历史。隐藏事件可从现有
恢复管理页面恢复。

### 4.4 创建入口

删除周课表空白时段和全天空白区域的点击创建行为。全局新增按钮继续作为个人事件和
Task 的统一创建入口，避免误触和重复入口。

## 5. Task 与 PlanBlock

### 5.1 Task 详情

周日程截止事项带、未定截止栏和 Task 中心点击 Task 后，统一进入 Task 详情页，不再
只显示标题 Snackbar。

详情页按 Task ID 加载：

- Task 基础信息和持久化状态；
- 北京时间派生的截止风险；
- 关联 PlanBlock；
- 待确认的 PlanBlock 结果；
- 可用的状态操作和最近一步撤回状态。

记录已经删除时返回原页面并给出明确提示。

### 5.2 截止时间输入

Task 表单将截止时间文本框替换为日期与时间选择控件：

1. 选择日期；
2. 选择时间；
3. 组合为 `Asia/Shanghai` 下的 `deadlineAt`；
4. 允许清除，恢复为无截止时间。

界面显示本地北京时间，持久化格式继续遵循现有模型，不引入第二套时间表示。

### 5.3 PlanBlock

Task 详情复用 `PlanBlockEditor`、`PlanBlockService` 和既有生命周期规则，支持：

- 为 Task 创建 PlanBlock；
- 编辑或删除已有 PlanBlock；
- PlanBlock 结束后确认已执行、跳过或重排；
- 再单独确认整个 Task 是否完成。

不增加执行中状态、完成百分比、实际执行时长或自动剩余工时。

### 5.4 单步撤回

Task 和 PlanBlock 的受支持本地写操作继续接入 `UndoService`。只保留最近一步，不形成
连续撤回栈。来源同步、重新认证和完全重置不可撤回。

## 6. 账号、凭据与完全重置

### 6.1 删除安全凭据

删除安全凭据只删除操作系统安全凭据库中的凭据记录，保留下列内容：

- 本地账号及学校账号绑定；
- 已导入的课程、考试和二课日程；
- 个人事件、Task、PlanBlock 和用户覆盖；
- 操作历史与非敏感设置。

账号摘要明确显示“需要重新登录”。此状态下发起同步时返回
`reauthentication_required`，不得表现为空操作或通用失败。

### 6.2 重新认证

账号页提供专门的重新认证入口。重新认证表单绑定当前本地账号 ID，并要求用户重新输入
完整学校账号。`LocalAccount` 保存不可还原的规范化账号摘要；删除安全凭据前确保该摘要
存在，删除后不保留可还原的完整账号。重新认证时先比较摘要，再沿用首次登录所需的密码
输入、可见浏览器和验证码流程。

成功后只补回安全凭据并重新验证学校身份，继续使用原本的本地账号分区，不创建新账号，
也不迁移或复制业务数据。若登录出的学校账号与原绑定不一致，认证失败且不修改现有
账号。

### 6.3 完全重置

完全重置需要二次确认，执行期间禁用重复提交。成功后清除：

- 当前本地账号及其级联业务数据；
- 安全凭据；
- 来源配置与同步状态；
- 用户设置和可撤回状态；
- 专用浏览器 Profile；
- 其他以当前账号为边界的本地记录。

重置完成后立即刷新路由认证状态并进入首次登录页面。任何步骤失败都显示失败位置；
数据库清理使用事务，不能留下半清理的本地账号。

## 7. 路由与组件边界

新增或接通以下应用路由：

```text
/events/:eventId
/tasks/:taskId
/accounts/:accountId/reauthenticate
```

路由只携带稳定 ID。页面负责通过 service/repository 加载当前状态。既有
`EventDetailPage`、`OverlapExpansion`、`ConflictEditor`、`TaskDetailPage` 和
`PlanBlockEditor` 作为交互主体，修复工作只补齐导航、数据装配和缺失操作。

同步顺序属于应用服务，不塞入 Widget；Widget 只负责处理用户登录决策并展示逐来源
结果。来源可见性属于有效事件查询，不在课表组件里临时过滤。

## 8. 错误处理与原子性

- SourceBundle 解析、账号校验或数据库导入任一步失败，都不替换上一份有效快照；
- 单个来源失败不阻止用户查看其他来源的最终结果；
- 登录窗口关闭、凭据缺失、账号不匹配和 Bridge 忙碌使用不同错误信息；
- 页面异步加载期间防止重复操作，卸载后不得更新 Widget 状态；
- 详情目标消失时安全返回，不抛出未处理异常；
- 删除个人事件、隐藏来源事件、Task 状态和冲突修改写入操作历史；
- 完全重置和来源同步不提供撤回。

## 9. 测试与验收

实现按以下修复组采用回归测试先行：

1. 数据库测试：完整快照淘汰旧考试；`outside_scope` 二课历史仍保留；用户覆盖不丢失。
2. 同步测试：严格顺序、登录恢复、取消登录、缺少凭据、一个来源失败和逐来源结果。
3. 日程测试：单事件详情、重叠两步选择、冲突编辑、前景主事件、隐藏和恢复。
4. Task 测试：详情路由、日期时间选择、无截止时间、PlanBlock 和单步撤回。
5. 账号测试：删除凭据、同一账号重新认证、身份不一致、完整重置和重置后导航。

自动验证至少包括：

```powershell
conda run -n ustc_assistant python -m unittest discover -s tests -v
conda run -n ustc_assistant python -m compileall -q src tests
flutter test
flutter analyze
flutter build windows --release
```

自动测试不得访问学校网站，也不得对真实用户数据库执行完全重置。自动验证通过后，
继续使用 `docs/acceptance/windows-first-milestone.md` 复测本轮失败项。真实 Edge
登录、验证码和学校页面采集由用户完成。

## 10. 完成标准

本次修复完成需要同时满足：

- 重复同步后旧考试不再出现在有效周日程中；
- 教务与二课在“全部同步”中依次完成，各自状态准确；
- 单事件、重叠事件、冲突和前景主事件均可通过 UI 操作；
- Task 详情、日期时间选择和 PlanBlock 形成完整链路；
- 删除凭据后明确要求重新认证，成功后仍使用原账号分区；
- 完全重置后本地账号消失并返回首次登录页面；
- 周课表只保留全局新增入口；
- 自动测试、静态分析和 Windows Release 构建通过；
- 人工验收文档中的对应失败项完成复测。
