## 继续生效的约束

1. 密码与模型 Key 受保护持久化、按需使用，不进入日志、审计、工具或非目标出站；浏览器认证资产保持不透明，存于受控分区。

4. 来源刷新保留用户覆盖；规划内容由用户确认；本地写、确认与必要审计同事务，失败不伪装成功。

6. 自动测试不访问真实学校网站；真实验收与自动结果分别记录；秘密、原始响应和会话资产不进入 Git 或日志；用户验收原结论不覆盖。

## 首轮问题

P1 表示关键安全、数据语义或来源可行性问题，应在相关设计冻结前解决。P2 表示需要重定方案或补齐证据的问题。下文保留首轮发现及原建议，出处均指对应文件的“历史设计资料”；不再使用修订前行号。八项的规则修订均已落实，验证状态以 [14 当前评审表](14-overall-review.md)和 [13 的 V-01–08](../quality/13-risks-and-acceptance.md)为准，不把文字修订当成实际验收通过。

### DR-01 P1 资源 URL 中的账号参数尚不能证明当前会话身份

**出处**：[07 ADR-003](../architecture/07-constitution.md)把当前文档的同源资源 URL 中 `fine_username` / `username` 视为权威，并从 JW 复用于 Young；同一条又明确证据类是否合法仍未决。[13 的 Young 观测](../quality/13-risks-and-acceptance.md)证明的是导航、会话复用与响应形状；文档入口另记真实尝试出现 `identity_unverified`。

Resource Timing 描述资源请求，包含页面脚本发起的请求，并可包含网络中止的请求；它不提供账号认证断言。[W3C Resource Timing](https://www.w3.org/TR/resource-timing/#resources-included-in-the-performanceresourcetiming-interface) 因此，仅同源且查询参数等于预期用户名，仍缺少“该值由认证后的服务端为当前会话返回”的信任依据。这是从标准与当前契约推导出的风险，尚未证明真实学校存在可利用路径。

**建议**：每个认证来源定义独立的身份证据契约，明确服务端业务响应、必要字段、会话关联与文档时效。会话健康、页面可达、身份匹配分别判定；JW 的成功规则不能直接证明 Young 可行。无法核验与确证串号统一区分，重新设计时不继承 JW 把所有未核验情况报为 `account_mismatch` 并清理的历史特例。

**关闭条件**：用户辅助观测 JW、Young 两种认证来源；形成不含秘密与原值的证据契约和结论。新合成样例验证匹配、不匹配、缺失、过期、客户端自报账号，以及“资源 URL 命中但认证响应未证明账号”等反例。用户确认登录不能替代程序核验。

### DR-02 P1 Storage 旁证与会话不透明红线冲突

**出处**：[07 §2.1、ADR-019](../architecture/07-constitution.md)禁止应用读取浏览器认证状态和各 Storage；[07 ADR-003](../architecture/07-constitution.md)及 [11 D-10](../architecture/11-component-designs.md)仍要求收集 Storage 账号旁证。

读取后仅返回布尔值，仍需要某段应用提取逻辑先读取 Storage，不能自动满足“不读取”约束。来源适配器也不应通过身份核验绕过会话资产边界。

**建议**：在现有红线下移除 Storage 核验路径，身份只使用经明确验证的业务数据。P 负责浏览器运行时会话生命周期，C1 仅消费必要的业务身份判定。若另选方案需要改变红线，应单独列明资产、读取方和理由，交用户决定。

**关闭条件**：07、平台端口、身份提取脚本和组件状态机采用同一规则；新脚本及返回契约不读取或携带 Cookie、Token、Storage、认证 header。

### DR-03 P1 首登回滚后持久会话分区可能失去归属

**出处**：[07 ADR-002](../architecture/07-constitution.md)要求持久分区；[09 CT-P-02](../architecture/09-contracts.md)允许核验后关闭时保存会话快照。[09 首登失败出口](../architecture/09-contracts.md)、[10 首登链路](../architecture/10-runtime.md)和 [11 D-26](../architecture/11-component-designs.md)只明确销毁内存上下文与 provisional debug 资产。

反例：学校登录与身份核验成功，账号提交随后回滚，或提交前进程崩溃。预分配账号尚无数据库行，其分区却可能已有认证资产。当前启动调和接口只覆盖 debug，没有明确认领、隔离和回收此类持久分区的入口。数据库零行不能证明会话零残留。

**建议**：为 P 管理的所有应用专用分区建立安全的生命周期登记，覆盖 provisional 创建、提交后认领、失败清理及崩溃调和。登记只含必要归属元数据，不含凭据；清理仅作用于本应用受控目录。正式账号的非破坏性身份核验失败，与未提交首登分区回收应分开定义。

**关闭条件**：模拟身份通过后提交失败、提交前退出、提交后认领前退出，以及清理失败重试。启动后只有已提交账号的分区可复用，其余分区可被安全识别并完成回收；删除失败不报清理成功。

### DR-04 P1 导航就绪缺少文档关联与失效契约

**出处**：[09 CT-P-01](../architecture/09-contracts.md)只有 URL、选择器和脚本接口；[11 D-09](../architecture/11-component-designs.md)把 URL、DOM、握手三位合并为 ready，没有定义它们必须属于哪次导航、哪个主文档及重试后的失效规则。

WebView2 的不同导航事件可能重叠，官方要求用 NavigationId 关联文档。[Microsoft 导航事件说明](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/navigation-events) 仅吸收乱序还不够：上一轮 DOM/握手与新一轮 URL 命中可能凑齐三位。页面用户操作或脚本也可能在检查后发起导航；执行脚本和消费消息时需要校验当前来源。[Microsoft 安全说明](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/security)

**建议**：平台事件携带会话实例、文档或导航标识；共享语义层按一次等待操作关联三种证据。重导航、重试、取消和关闭使旧回调失效；主文档与 frame 分开。填表限定于实际认证 origin，并在执行时验证；业务提取与返回校验绑定当前文档。

**关闭条件**：合成导航重叠、重定向、旧握手迟到、frame 消息、取消后回调，以及检查后跳转的反例；不得产生错误 ready、跨文档提取或向非认证页面填入密码。

### DR-05 P1 来源缺失自动退出日程与用户隐藏语义冲突

**出处**：[07 §2.2-2](../architecture/07-constitution.md)规定学校记录仅经用户明确同意本地隐藏；[09 SourceBundle](../architecture/09-contracts.md)规定 `missing_within_scope` 被有效事件流过滤；[11 D-20](../architecture/11-component-designs.md)将该过滤写入投影算法，[03 来源状态与有效事件流](../archive/2026-10-11-before-reorganization/docs/refactor-docs/03-data-storage.md)也保留相同历史行为。

同一范围的新快照未返回一条旧课程时，该课程会在未经用户确认的情况下退出课表，并可能退出提醒与冲突计算。保留数据库行仍不能解释它与“仅用户同意后隐藏”的关系；错误空快照会放大影响。

**建议**：区分采集不完整、来源未再观察到、学校明确撤回和用户隐藏。候选默认行为是保留已知记录并标示来源缺失；是否继续计入提醒、冲突及当前日程由产品规则明确决定。若允许学校确证撤回后自动退出当前日程，应明确该业务状态与用户隐藏的区别并回写约束。

**关闭条件**：用户确认缺失记录的展示语义；验证合法空快照、不完整响应、窗口移动、确证撤回、再次出现及已有 UserOverlay。页面、Agent、提醒、冲突采用同一解释。

### DR-06 P2 数据迁移仍假定唯一资产是旧 v7 库

**出处**：[07 ADR-011/012](../architecture/07-constitution.md)、[09 §7.1–7.2](../architecture/09-contracts.md)和 [11 D-01](../architecture/11-component-designs.md)固定 v7→v8、27→30 表；当前 [文档入口](../README.md)说明 main 已换成 minimal，另保留暂停的 flutter-native 工作区。

本轮未检查私有数据库。现有材料不能证明用户需要迁移的资产只属于 v7，也不能证明新设计应沿用旧 30 表。直接采用该前提可能漏掉需要保留的数据。

**建议**：先列实际资产类型、版本、迁移范围与保留要求，再定义新 Schema 和必要迁移路径。普通业务数据与浏览器会话资产分开；新工程和旧工程的数据目录独立，迁移与回退只操作受控副本。

**关闭条件**：用户确认资产范围；按重新定义的合成数据验证标识、覆盖、状态、审计及回退。实际资产的人工验收单独记录，不把旧迁移通过结果算作新证据。

### DR-07 P2 并存施工架构需要按从零构建重定范围

**出处**：[08 §8](../architecture/08-target-architecture.md)设计 Python 租户；[15 §3](../workflow.md)要求来源默认 Python、旧 oracle 常驻及短分支回合入。这些是历史施工方式，本分支 AGENTS.md 已指定单 agent、从零实现、不直接复用旧代码及流水线。

**建议**：保留来源注册、单作业仲裁、事务内租约校验和测试替身等必要机制；新工程不默认构建 PythonProcessPort、LoopbackBridgeTransportPort 和 Python 运行通道。真假来源的选择用于新契约验证，每条真实来源独立实现与验收。旧工程留在原 worktree 作为可运行参考。

**关闭条件**：08–15 的新有效设计和精简施工顺序不依赖旧租户、旧 gate 或旧测试全集；来源契约按当前需求重新定义。此项是待修订的方案范围，不把历史记录本身判为当前施工违规。

### DR-08 P2 浏览器能力证明应前移，三端接口一致尚属目标

**出处**：[08 §5.6、§6](../architecture/08-target-architecture.md) 保留三端替换目标、具体包待 M2；[13 R-01/R-05](../quality/13-risks-and-acceptance.md) 记录的是原分支证据或延期验证。官方 `webview_flutter` 当前列出的支持平台为 Android、iOS、macOS，Windows 适配器需单独选择并验证。[Flutter 包官方页面](https://pub.dev/packages/webview_flutter)

UDF 真删除需要结束会话并等待占用它的浏览器进程退出，关闭控件不能直接作为删除完成条件。[Microsoft UDF 管理说明](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/user-data-folder) 冷启动复用、SessionStorage 等状态的生命周期、取消和真实身份提取也需由所选适配器证明。

**建议**：在整体设计冻结前，以可丢弃的最小验证确认 Windows 适配器需要的能力；先用合成页面验证平台行为，再由用户协助核实真实 CAS 与来源。验证代码不直接变为产品工程。Android、iOS 维持目标与待验证状态，能力矩阵逐项记录。

**关闭条件**：新证据覆盖可见登录、隔离、跨重启复用、取消收口、文档关联和真清理；真实来源的身份与响应契约可行。自动通过与人工通过分开，失败如实保留。

## 已采纳的架构方向

保留 C0–C5 与 P 的职责边界，先作为单 Flutter 工程中的模块组织，不增加部署或包拆分要求。C0 只保留跨模块稳定的时间、错误及必要值对象；来源与平台端口放在其职责归属处，避免共享核心成为业务杂项集合。

- C1 管理来源执行与会话语义，来源各自声明身份、请求、导航、响应与完整性契约；不写库。
- C2 是来源作业唯一入口，管理同一作业的暂停、恢复、取消与交接。需要区分“来源终态载荷可见”“浏览器资源已收口”“导入或交付已完成”；全局租约在必要收口完成后释放。
- C3 是本地事实与事务权威，定义新数据模型；在提交事务内检查账号、维护状态、来源 generation 和 reset epoch；正式业务与用户覆盖连续保留。
- C4 只通过 C2 查询来源，通过 C3 服务读写本地数据；工具权限与模型出站分别检查，模型不能取得凭据或直接驱动浏览器。
- C5 负责界面、组合根和跨模块用例编排；P 承担浏览器、安全存储、文件、通知等平台能力；维护恢复先于正常使用。

上述职责及关键约束已写入 07–15 顶部的当前规则。各文件原正文完整保留在历史区；不沿用其冻结状态、接口签名或 Schema 版本。当前决定见 07 的 DR-ADR-01–08，关键契约见 09 的 K-01–06，修订与待验证状态见 14。

### DR-09 P1 活文档核验与关闭后提交缺少交接规则

**出处**：[09 K-01/K-03/K-04](../architecture/09-contracts.md)当前第 13、45、57 行要求身份判定仍属当前文档、关闭使旧操作失效，并要求终态后资源收口；[10 首登步骤 5](../architecture/10-runtime.md)第 17 行先产生终态并收口，再由 C3 提交。

**失败场景**：C1 在文档有效时核验并采集，关闭浏览器后文档 token 失效，C3 才收到快照。若 C3 仍要求活文档，本来合法的首登无法提交；若直接跳过有效性检查，又没有明确的已验收产物边界。当前没有区分“允许继续操作页面”与“已经采集并验收的数据可提交”。

**建议**：选定一致顺序：提交后再关闭，或在文档仍有效时封存不可变的采集产物及可信上下文，随后收口。后一方案中，关闭只撤销页面操作能力；C3 按产物绑定的账号、job、契约版本、generation/epoch 和完整性验收，取消或维护仍使旧产物不能提交。封存只能由受控来源链产生，不能由 UI/Agent 任意拼装成功判定。

**关闭条件**：合法采集在关闭后可按选定契约完成提交；采集期间切文档、封存后取消/reset、伪造交接和重复交接均有确定结果。先修订 09–11，再按 V-01/V-02/V-06 验证。

### DR-10 P1 全局作业与启动调和缺少进程独占前提

**出处**：[08 来源仲裁](../architecture/08-target-architecture.md)第 27 行与 [09 K-04](../architecture/09-contracts.md)第 53 行定义 C2 全局租约；[10 启动流](../architecture/10-runtime.md)第 9 行会回收无已提交 owner 的分区。[11 分区状态机](../architecture/11-component-designs.md)第 23 行也执行该回收。当前没有应用实例或同一数据目录的进程所有权契约。

**失败场景**：实例 A 正在首登，已创建 provisional 分区但尚未提交账号；实例 B 启动时从数据库看不到 owner，把 A 的在用分区当作崩溃残留。两个实例也可能各自取得进程内 C2 租约，同时执行来源、迁移或维护。“单账号”没有解决这类互斥。

**建议**：Windows 首版明确同一应用数据目录的单活动进程，在打开库、读取归属、调和或启动任何作业前取得排他所有权；第二实例转交激活或安全退出。若选择多实例，必须另定义跨进程作业和资产所有权，不能沿用单 C2 假设。

**关闭条件**：双实例启动、首登中再启动、维护中再启动与持有者崩溃后重启，不出现双作业或在用资产回收。调和只由已取得排他所有权的实例执行；纳入 V-02。

### DR-11 P1 本地写入缺少持久命令回执与审批内容绑定

**出处**：[09 K-05](../architecture/09-contracts.md)第 63 行只对导入明确幂等；K-06 第 75 行对本地写定义版本复验和同事务审计。[13 V-06](../quality/13-risks-and-acceptance.md)尚待审核完整工具及写契约。当前没有本地写命令身份、持久回执及被批准参数的定义。

**失败场景**：创建任务已提交，进程在 UI/Agent 收到成功前退出；重试又创建一条。创建操作没有既有目标版本，不能仅靠 stale_target 防重。确认卡也未明确绑定哪一份不可变参数、目标集合和权限版本；仅写“执行时复验”不能让生产与消费方一致实现。

**建议**：UI 与 Agent 共用 C3 命令协议。由受控入口分配稳定操作身份，绑定账号/epoch、规范化动作及参数、目标版本和必要批准；业务、确认、安全审计及持久回执同事务。相同命令重放返回已有结果，身份相同但内容不同拒绝；批准后参数改变须重新确认，执行时复验当前权限。回执中的内部定位信息与不含 id/ref 的审计摘要分开。

**关闭条件**：双击、同一确认重复提交、提交后回执丢失、重启后查结果、批准参数变更和权限撤回有确定结果；不重复业务、不伪造成功，不靠重复模型请求或内存指纹保证幂等。归入 V-06。

### DR-12 P2 凭据持久化与账号事务的衔接尚未定案

**出处**：[07 安全约束](../architecture/07-constitution.md)第 20 行要求密码/Key 受保护持久化；[08](../architecture/08-target-architecture.md)第 19、39 行保留平台安全存储；[09 K-06](../architecture/09-contracts.md)第 75 行与 [10 首登步骤 5](../architecture/10-runtime.md)第 17 行的提交清单未明确凭据，10 第 46 行又要求事务更新凭据。

**失败场景**：若平台独立保存秘密，先写秘密再提交账号可能留下孤儿；先提交账号再保存则可能在中间退出，留下未完成的持久化承诺。若 P 只提供加密能力、密文随 C3 SQL 事务保存，则需要明确该选择，避免被实现为两个独立存储提交。

**建议**：区分“保护/解密端口”和“秘密存储端口”，选定一种提交模型。密文随业务库提交时明确首登、换密钥、删除及回退范围；外部秘密存储则需要暂存、认领、回收和启动调和。密码与模型 Key 分别定义，不能直接继承旧 DPAPI 存储方案为已验证选择。

**关闭条件**：首登及重新认证的凭据归属、提交点、清理失败和崩溃恢复明确；持久账号不依赖已丢失的内存租约，未提交账号不留下可复用秘密。存储方案在冻结前定案，平台与迁移验证分别完成。

### DR-13 P1 提醒缺少持久协调与维护收口契约

**出处**：[09 K-05](../architecture/09-contracts.md)第 63 行与 [10 同步流](../architecture/10-runtime.md)第 24 行将提醒协调放在提交之后；10 第 48–50 行维护只明确等待来源和 Agent。[11 投影](../architecture/11-component-designs.md)第 60 行又要求隐藏同步调整提醒，当前没有通知在途回调的守卫及启动重建规则。

**失败场景**：业务提交后、协调启动前崩溃，尚未记录“失败待重试”；重启可能漏掉协调。清业务数据或 reset 完成后，旧定时器/平台队列仍可能投递旧记录，库内写屏障并不能自动撤销平台副作用。

**建议**：业务事务同时更新期望提醒及持久协调依据，平台投递在事务外幂等执行并在启动时对账。投递关联账号、epoch 与提醒版本，执行前检查当前有效状态；维护先停止调度并处理在途投递、取消已登记平台通知，再按真实清理结果收尾。平台已接收但本地未记回执的情况明确为待对账，不承诺未经证明的恰好一次投递。

**关闭条件**：提交后立即退出、隐藏时在途回调、清库/reset 后旧定时器、取消平台队列失败和投递回执不明均有稳定结果。维护与协调契约在冻结前明确；各平台可靠性按 V-08 分阶段验证。

### DR-14 P1 Agent 清历史与撤权缺少独立运行守卫

**出处**：[07 用户清除能力](../architecture/07-constitution.md)第 22–24 行保留权限变更与 Agent 历史清理；[10](../architecture/10-runtime.md)第 26 行明确来源与模型是两种状态机，第 37 行定义的是来源 generation 失效；[12](../architecture/12-cross-cutting.md)第 18 行只规定出站字段检查。当前没有 C4 清历史、撤权后的流式消息、摘要与在途请求收口协议。

**失败场景**：用户清除历史后，旧模型流或后台摘要迟到，再写入被清除的内容；用户撤销联网授权后，暂停运行继续下一次调用。当前账号和 reset epoch 没变，单靠来源作业戳不能区分这些旧运行。

**建议**：为 Agent 定义运行与会话所有权、清理/取消状态及可撤销授权。清历史先阻止新运行、收口或作废旧流/摘要/确认，再提交清理；每次聊天落库及新增模型/来源请求复验对应会话世代和当前授权。历史、摘要、工具结果及模型重试统一经过出站投影。已发送请求不能被记作已撤回；撤权必须阻止后续新增请求。

**关闭条件**：流式生成中清历史、摘要中清历史、暂停时撤权、禁用 Agent 后迟到结果和重复确认，不重建内容、不新增未授权出站；来源作业和 Agent 运行各自收口。归入 V-06。

### DR-15 P2 关键业务模型只保留能力，尚缺新语义定义

**出处**：[07 产品范围](../architecture/07-constitution.md)第 11–16 行保留稳定身份、覆盖、重复、Task/PlanBlock 与撤销；[09 K-05](../architecture/09-contracts.md)第 61 行和 [11](../architecture/11-component-designs.md)第 5 行均将完整模型留待后续。[03 数据字典](../archive/2026-10-11-before-reorganization/docs/refactor-docs/03-data-storage.md)仅是旧实现参考。

**失败场景**：学校调整课程时间，若发生项身份随时间改变，旧备注、出勤与任务关联无法挂回；重复系列拆分后，单次例外和冲突规则可能指向旧系列；撤销若恢复整行，可能覆盖其后同步的新来源字段。仅要求“稳定身份”和“UserOverlay 保留”还不能决定这些结果。

**建议**：先定义精简领域模型及不变量，再落新 Schema：学校事实与用户决定分层，课程系列/发生项和个人重复系列/发生项分别有稳定定位；字段清除、继承和覆盖优先级明确；时刻/日期/全天、区间边界及重复展开范围明确；Task 与 PlanBlock 生命周期、关联迁移、复合写和撤销的版本/原子边界明确。UI、Agent、提醒与冲突共用这些定义。

**关闭条件**：改时、窗口变化、系列拆分、单次例外、关联目标变化、同步后撤销、批量部分失败及跨午夜/全天均能按模型推导出唯一结果。关键模型在冻结前审核，完整字段和切片验证按 V-04/V-05/V-06 补齐；不要求继承旧表数。

### DR-16 P2 资产清点被迁移前置条件限制

**出处**：[11 迁移状态机](../architecture/11-component-designs.md)当前第 66 行规定“清单和目标映射不完整不得读写实际资产”；[09 K-06](../architecture/09-contracts.md)第 71 行与 [13 V-04](../quality/13-risks-and-acceptance.md)要求先确认实际输入和版本。

**失败场景**：为了确认旧库版本和关系，必须先检查必要元数据；但目标映射尚未完成时，该条又禁止任何读取。只能依赖用户猜测版本，不能完成有依据的资产清单。

**建议**：区分只读资产清点、受控副本转换和目标发布。允许在明确范围内读取必要格式/版本/关系元数据形成脱敏清单；转换前才要求完整映射与一致副本，发布前要求完整性和语义验收。原件保持只读，秘密与原始行不进记录。

**关闭条件**：无需先读秘密或修改原件，就能确认实际资产输入；清点、转换与发布各有准入条件。回写 09/11/V-04 的边界，不把清点等同迁移通过。
