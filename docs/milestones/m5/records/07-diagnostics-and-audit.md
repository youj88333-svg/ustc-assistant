# M5.7：参数修复、运行诊断与整体自检

日期：2026-10-14。设计依据为 [07–12](../../../architecture/07-constitution.md)、[13](../../../quality/13-risks-and-acceptance.md)、[14](../../../reviews/14-overall-review.md)、[15](../../../workflow.md)及 [唯一任务单 §19](../plan.md#19-m57参数修复可导出诊断与整体自检)。用户要求持续完成修复、日志和整体审查，不等待中间人工监视；M5 最终真人验收与工程检查分开。

## 1. 实际问题与修复边界

用户截图中，安排一小时作业的请求经过日程、空闲和任务查询后，两次“准备本地修改方案”被拒绝，最终没有回复。旧摘要只含 `invalidRequest`，没有实际字段原因；本轮不能反推出当时模型到底发错哪一项，也没有读取正式对话、业务库或模型 Key 补猜原因。

根修复可确定的契约缺口：15 种本地动作的必填/可选字段集中到 `agent_change_spec.dart`，同时驱动原生校验与模型说明。提示明确新任务 `local_key`、后续时间块 `task_key`、依赖顺序、北京时间格式、`slot_ref` 与起止时刻互斥、未知字段省略而非 null。只有截止日期时不猜具体小时，新任务描述保留日期，精确 deadline 仍需精确时刻。

拒绝结果增加编译期 `validation`（原因、字段、动作、0–19 项索引）和对应修正说明。未知键名和值不回显。模型可按反馈修正一次，再次错误明确显示参数失败，不误报工具不存在；方案准备仍零业务写，只有当前具体卡经用户批准才提交。空回复错误显示真实未完成状态，并可导出日志。

合成闭合验证已覆盖“缺少 local_key → 收到明确反馈 → 正确任务加块 → 等待批准时零写 → 批准后一次提交”，以及重复错误、null/额外字段、引用/时间错误、停止与已提交事实。真实原句和所选模型的新回复质量仍待用户复验。

## 2. 方法与分工

采用 [Anthropic 工具设计](https://www.anthropic.com/engineering/writing-tools-for-agents)中的清晰契约、可修正错误及范围控制；参照 [Agent 评估方法](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)，分别检查调用轨迹、实际持久结果及用户体验。安全/批准/事务由确定性代码判定，真实语言和视觉质量保持人工待验。

诊断参考 [OpenTelemetry 日志数据模型](https://opentelemetry.io/docs/specs/otel/logs/data-model/)的时间、事件和关联概念，以及 [OpenAI Agents SDK 敏感追踪说明](https://openai.github.io/openai-agents-python/tracing/#sensitive-data)提醒的输入输出捕获风险；本项目自行实现白名单本地日志，不引入云 SDK、Collector、自动上传或自由 metadata。框架/异步错误接入参照 [Flutter 错误处理](https://docs.flutter.dev/testing/errors)，只记录固定错误类别，debug/test 保留原报告器，Release 不输出原始异常和堆栈。

Sol / max 负责共享规格、C4/P/C5 装配、跨层修复和根检查。Luna / max 承接已定契约的 journal、导出 UI、独立 Agent/日志/运行测试及原生 fixture 清理，各自文件不重叠；Astra 独立只读复核权限、上下文、协议和文件生命周期。子代理通过声明不替代下列根实际结果。

## 4. 日志、导出与定位

正式所有权先于 `diagnostics/` 访问，固定 `diagnostic-0.jsonl` 至 `diagnostic-3.jsonl`；每段 256 KiB、总上限 1 MiB，队列 128、单事件 2 KiB。打开、记录或导出时淘汰超过 7 天的事件。损坏/超限/额外字段只形成安全计数，不复制原文；静态 reparse/junction、非普通文件和所有权丢失拒绝。该路径约束不承诺抵抗同一 Windows 用户的实时恶意篡改。

事件包括启动/收口、Agent 运行、模型请求、工具结果、批准/拒绝、停止、配置/历史/来源/维护。每条保留产生时的应用版本、schema、工具、提示词和构建 SHA，升级后的导出仍可区分旧事件版本；随机 trace 只用于诊断，没有账号/owner/run/业务 ID 映射。schema 保持 13，不新增业务迁移。

“设置 → 数据与隐私 → 运行诊断”和 Agent 错误处可主动导出 JSON；一次最多 1000 条，重验证合法记录并报告覆盖/截断/丢弃/坏行。文件选择取消零写，静态链接/重解析目标拒绝；保存成功后由用户自行发送。清日志双确认，保留业务、Key、密码、历史；清历史/业务不自动清诊断，完全重置尽力清诊断，诊断故障不反转已完成业务。退出排空在释放所有权前完成。

目录不安全或所有权未取得的启动失败只启用内存日志，导出标记 `startup_error_only`、complete=false，界面说明没有读取既有日志。不能借错误导出入口打开本来被拒绝的资产。

`app/tool/diagnostics_summary.dart` 只分析主动导出的有界安全 JSON，按最近 20 条运行轨迹汇总失败字段、原版本和已提交工具/阶段；未知异常归固定类别。无网络、环境秘密、正式库或浏览器读取。日志可用于构造同版本合成复现；它没有私人原文、参数值或原始堆栈，不能保证重播所有实际问题。使用方法见 [应用说明](../../../../app/README.md#目录与诊断)。

## 5. 实际失败与修正

- 首次参数测试暴露构造器语法错误及范围继承过宽；修正后再跑，旧失败没有记作通过。模型事件包装替换时曾误改成自递归，相关测试挂起后根定位并改回调用实际 gateway，随后协议/停止测试和全套通过。
- 新原生诊断套件首次的 junction 测试试图改名已被 ownership 固定的目录，Windows errno 32 拒绝；测试改为获取所有权前构造静态 junction，保留生产守卫，重跑两组通过。
- 首次十目标合并 Windows 命令未通过：Agent 五组清理白名单不认识新增 diagnostics 子目录，后续套件遇 SDK 调试连接读器停止。清理辅助仅验证 fixture 自建正式根下四个固定普通文件、canonical 路径和 256 KiB 上限，不读取日志正文；demo/未知条目仍拒绝。根改为每个套件独立 SDK 命令逐套重跑，不能将失败批次算为通过。
- 最后复核新回归先检出来源 closing→idle 未提交仍记 complete，修订为 closed 后定向 16 项通过。配置测试初版把另一个 rejected 操作的开始事件混入断言，改为按实际 committed trace 分组，定向 10 项通过。最后静态检查检出一处格式展开后的 if 缺少花括号，补齐后根 analyze 无问题。均没有访问真实资产或放宽业务守卫。
