## 设计依据与目标

从 [文档入口](../../README.md) 阅读 07–12、[13 验收登记](../../quality/13-risks-and-acceptance.md) 和 [工作流](../../workflow.md)。具体接口依据 [Young 来源契约](../../reference/sources/young.md)，凭据共享依据 [学校认证决定](../../decisions/school-credentials.md)。不采用历史旧 M2/M3 编号。

目标是两项分别验收的能力：学校个人日历中的活动关联日程同步，以及报名活动列表/必要信息的独立只读查询。

## 范围与不变量

- 独立 Young 分区、业务身份 verifier 和具体许可；与 JW/M0 共用浏览器平台和全局作业租约。
- 用户批准以活动关联记录为同步依据，排除未关联记录；活动关联不宣称独立核验本人报名成功或取消。
- 同账号使用 C3 已有的一份受保护学校密码，固定认证文档单次投递；挑战/授权仍人工，不共享浏览器认证资产。
- 门户与 CAS 根回调等待自然业务子路由，业务准备不授权读取；正式步骤仍绑定默认 context、确切脚本、主文档和操作。
- 活动读取完整分页，只在内存展示必要信息，不导入日程、不执行报名/退出/签到/申报。
- 日程按开始前选择的北京时间范围逐日读取全部页，仅接受完整响应；规范化、合并一致重复、冲突拒绝，经封存及 C3 事务导入。
- 来源缺失和范围外保留，更新不丢本地身份/隐藏设置；取消、关闭、重启、清 Young 登录资料不丢已提交事实。

## 分工、依赖与验收

Sol / max 负责设计、原生关联、状态/许可/事务和最终验收；Luna / max 限定实现 DTO、UI、测试或夹具；Astra 按需独立复核。各切片文件边界和模型实际调用保留在对应记录，SDK 由根串行执行。

依赖顺序为二课观测 → 真实业务身份/两个只读契约 → 应用内固定主动验证 → 正式查询和导入 → 共享认证与兼容性 → 生命周期及连续性验收。保留既有 JW 密码、目录、业务数据与 M0/M1 验收；自动测试不访问学校或正式资产。

完成条件包括身份与完整性反例、事务/迟到结果守卫、全局互斥与排空真清理的本机检查，最终 analyze/test/相关 Windows/build，以及真实全自动查询/同步、必要信息/日期时间、重启不重复、隐藏恢复、取消再同步、清登录资料后两来源连续性的用户验收。
