# 晨报日期窗口与展示修订

日期：2026-10-15。依据 [09 K-07/K-09](../../../architecture/09-contracts.md)、[10 运行链路](../../../architecture/10-runtime.md)、[11 组件](../../../architecture/11-component-designs.md)、[校园来源](../../../reference/sources/campus.md)、[M6 任务单](../plan.md)及[用户反馈](../acceptance.md#晨报体验退回修订2026-10-15)。本次只修晨报与公开日期元数据，不改变提醒平台、正式资料、凭据、同意或开关。

## 实际根因

安全日志当时只留下 `morningBriefStarted` / `morningBriefCompleted`，无法区分提供方错误；没有读取正式业务库或缓存来补推结论。根另以显式 `--public-notices-only` 手动启动固定匿名通知诊断：全新内存库、不使用模型/会话，只输出提供方、页数、覆盖和固定错误码。此操作是用户所报问题的有限公开诊断，不属于自动测试。

| 相同链路 | 实际 HTTP 尝试 | 教务 | 财务 |
|---|---:|---|---|
| 修复前 | 10 | 5页、0日期未知、`resourceLimit`、不完整 | 5页、0日期未知、`resourceLimit`、不完整 |
| 初版日期修正 | 2 | 1页、0日期未知、无失败、昨天范围完整 | 1页、0日期未知、无失败、昨天范围完整 |
| 加后续真实页复核 | 4 | 2页、0日期未知、无失败、昨天范围完整 | 2页、0日期未知、无失败、昨天范围完整 |

根因是晨报总在历史列表里读到5页上限，未利用已登记时间线的日期边界，且把有界遍历结束误标为来源失败。两个来源在本次实际请求中可读；不能把旧 `resourceLimit` 误解释成代理/TLS/登录故障。修复后的两个登记栏目昨日匹配数为0，只证明所查日期/栏目，不是全校无公告。

另确认两处问题：手动重试仍复用原失败批次；模型虽收到覆盖提示，仍可能在自由文本中写出“没有新公告”。截图中的该句不能作为验证证据。

## 修正与保留

- C1 仅对固定无关键词通知栏目验证合法日期和非递增顺序，剔除明确置顶；C2 传递当前页排序元数据。晨报自身复核已读顺序，越过昨天日期后再验证一个后续真实页；同页缓存切片不能充当确认。来源从新到旧是显式登记契约，不能仅凭页内排序推断未知网站。未知/乱序继续有界读取，达到页数上限只报部分覆盖。服务指南、搜索等不获时间线声明。
- 手动重试重新查询公告；中断恢复只复用完整批次。没有自动删除正式缓存、清业务或增加每天无界请求。
- 内部模型结果区分今日/公告两段，不显示原始 JSON 或尚未解析的流。来源不完整时直接用应用生成的今日事实版，不调用模型；现有通知条目仍可在详情读取，所有旧模型摘要（含其today字段）在覆盖不足时都不展示。避免用字段形状或提示词充当语义证明，完整批次仍是一个无工具后台请求，保留主聊天优先和预算。
- 日志为每提供方保存固定阶段、覆盖结果、失败码、成功页数，关联独立随机诊断号；不记正文、标题、URL、日期事实、模型内容或业务ID。
- 默认48像素单行晨报入口，完整内容在可关闭阅读面板显示；本次应用会话可隐藏当天入口，标题区小图标恢复，切页/后台结果不强制恢复，次日重新显示。“和 Agent 讨论”移除，不写聊天或发送消息。
- 两个明确子任务由 Luna / max 承接 UI 与排序元数据，Sol 负责诊断、关键协调/缓存/摘要/日志和根集成；代理声明与根实测分开。
