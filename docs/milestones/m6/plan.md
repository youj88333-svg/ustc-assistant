## 1. 目标、依据与当前缺口

| 目标 | 本阶段交付 |
|---|---|
| 每日晨报 | 北京时间每天 06:00 后首次使用，先显示当天本地事实，再异步补昨天教务/财务通知与简短模型摘要；打开页面、操作日程和主动聊天不等待晨报完成 |
| 系统提醒 | 每个有提醒时间依据的日程可设置两个槽位，定时日程默认提前 30 分钟、第二次关闭；由 Windows 保存计划，应用完全退出后也能投递已登记提醒，并支持改期、取消、重启对账和点击定位 |
| 未来移动端 | 复用提醒规则、期望账本及协调契约；本期交付 Windows，Android/iOS 原生权限/调度及真机验收留待对应阶段 |

现行依据为 [07](../../architecture/07-constitution.md)、[08](../../architecture/08-target-architecture.md)、[09 K-06/K-07/K-08](../../architecture/09-contracts.md)、[10](../../architecture/10-runtime.md)、[11](../../architecture/11-component-designs.md)、[12](../../architecture/12-cross-cutting.md)、[13 V-05/V-06/V-08](../../quality/13-risks-and-acceptance.md)、[14 审查方法](../../reviews/14-overall-review.md)、[15 工作流](../../workflow.md)及[校园来源契约](../../reference/sources/campus.md)。平台验证后在 M6.1 把确定接口/规则写入 canonical 设计；既有权限、保留承诺或已关闭阶段的证据继续有效。

只读源码盘点确认：

- C3 已有课程、考试、Young、个人重复日程/单次例外、出勤/隐藏和任务时间块的一致投影。`CalendarQuery` 单窗最多 62 天、500 项，存在截断标志；提醒规划不能把截断当完整集合。
- 现有代码没有提醒表、提醒偏好、OS 通知端口或通知依赖。09–12 中“业务/期望提醒同事务、平台事务外协调”是现行设计约束，尚不是已实现能力。
- 校园端口已有教务与财务通知分页，但没有日期筛选参数；`publishedOn` 是可空原样字符串，续页为有期限的内存游标。晨报需要补来源日期归一化和覆盖判定。
- 当前为普通 Flutter/Win32 Release，退出会结束进程；没有 MSIX 配置或常驻进程。当前 schema 15，拟以 15→16 增量保存本阶段新增资产。
- 主聊天使用独立运行状态和唯一持久对话。晨报不可直接调用主聊天 `send` 并占用其 busy 状态；模型网关、Key 安全租约和固定出口可以复用。

## 2. 本期边界与建议默认值

下列规则已随本计划获批。应用内两个功能各自的一次启用及模型同意仍由用户主动操作，施工批准不替用户开启设置。

| 项目 | 建议规则 |
|---|---|
| 昨日通知来源 | M3 已登记的教务处“通知新闻”及财务处“通知公告”；不扩成全校网站抓取，不包含评课新点评或把所有服务指南当新闻 |
| 今日安排 | 复用日程页当天有效投影，呈现课程、考试、二课、个人安排和时间块；未完成的当日截止任务单列，过期任务只给必要计数。隐藏项不默认展开，计划不参加/已跳过等状态如实保留，不误说仍须参加 |
| 定时对象提醒 | 课程、考试、Young、个人定时日程、任务时间块，以及有具体截止时刻的未完成任务；默认第 1 次提前 30 分钟、第 2 次无 |
| 全天对象提醒 | 两个槽位仍保留，但用“相对日期＋北京时间时刻”而非伪造午夜开始；**第 1 次当天 09:00，第 2 次无**，可改为前一天等日期/时刻。这是已批准的定时规则例外 |
| 无截止任务 | 不猜提醒时刻；显示需先设截止时间，可通过其已安排时间块获得提醒 |
| 不活跃对象 | 隐藏、单次跳过、个人出勤计划不参加、已完成/取消的对应对象默认不提醒；学校来源缺失/未确认撤回仍按原保留规则处理，不静默取消 |
| 任务与时间块 | 任务本体完成/取消仅影响其截止提醒；时间块按自身状态处理，不自动改块状态。两者可能各有提醒，界面标明对象，用户可分别关闭 |
| 用户启用 | 设置中分别开启自动晨报和系统提醒。启用晨报说明公开联网、当日基本日程发往已同意模型及用量；启用提醒说明可能显示在系统/锁屏。开启后不每天再确认；既有模型 Key/同意及 OS 设置仍有效 |
| 两主页 | Agent/日程两主页不变；晨报是 Agent 页紧凑卡片，提醒控件放日程详情/编辑器，设置增加辅助分组，不挤占周视图画布 |

本期不引入常驻服务、托盘代替退出、云推送服务器、后台学校自动登录/采集、Agent 通知工具、额外模型供应商、移动端产品或应用自动下载附件。M5 已知语音识别问题独立跟踪，不记作 M6 功能或已修复。

## 3. 晨报：先给可用内容，再补生成

### 3.1 触发与每日身份

所有日期和 06:00 阈值按北京时间，使用现有 `AppClock`。唯一日键包含 owner、reset/brief epoch 和北京日期。

- 启动、从隐藏/最小化恢复到前台时检查当天资格；06:00 前不生成。已在前台使用且跨过 06:00 时可触发一次，隐藏/退出状态不为了晨报唤醒应用。
- 当天已有完成/进行中结果则复用，不因反复切页或重启重复生成。晚间才首次打开仍提供当天内容；隔了几天只生成当前日，不补多份旧晨报。
- 单个作业原子领取。进程中断后恢复为可解释状态，读取已保存阶段，不将失去响应当可无限重发。

### 3.2 页面与模型请求分离

采用“缓存先显示、后台更新、单次作业去重”的成熟模式，并按本地应用调整：

1. 主窗口首帧及聊天就绪后，异步读取今日快照/同日已缓存晨报。**不把公告网络或模型请求放进应用启动 await 链**。
2. 确定性呈现今日安排、首个未开始事件、冲突及任务截止等基础事实。没有模型、离线或模型失败时，这部分仍能使用；来源尚未同步不能说“学校今天没课”。
3. 后台读取公告。卡片自身显示“正在更新公告”，主对话输入和日程操作继续可用。
4. 准备有界事实包，进行一次无工具的摘要请求，流式更新卡片。模型仅归纳措辞，不重算课程时间、不创建事件、不刷新学校来源、不执行公告中的指令。
5. 完成后保存同日结果，后续打开直接读取；摘要失败保留事实版/已取得公告，提供重试，不显示整页失败或假装完整。

这不是声称让学校推理更快。方案隐藏等待并压缩输入/输出，不能保证服务端 TPS、排队或取消后的计费行为。

### 3.3 主动聊天优先

增加应用内轻量模型作业仲裁，晨报与主聊天使用独立请求/取消资源：

- 任一主动 Agent 运行（含等当前卡或学校挑战）优先，晨报模型请求先排队；不同时抢学校服务的单用户吞吐。
- 用户开始聊天时，尚未发出的晨报继续等待；已在生成则立即作废晨报交付资格，主动 abort 其独立传输。本地取消/租约收口设短而确定的上界，建议 2 秒；主聊天不等待服务端停止推理、流自然结束或迟到回调。无法及时收口的晨报资源隔离为失败/恢复待办，不保留前台锁或循环重试。不得调用全局关闭去终止主聊天、来源作业或共用配置；取消不保证学校服务端已经停止计算。
- 基础日程/公告卡保留，暂停原因简短显示；同日自动模型请求最多 2 次（含一次因失败/让路后的受控再试），连续取消不循环重启。用户可主动重新生成。
- 晨报同样让路 C2 已有来源租约，不抢占正在登录/同步的来源；平台本地提醒不占网络租约、不等晨报。

默认摘要输入估算上限 4000 token、输出上限 600 token，目标约 300–500 字中文；每次尝试只进行一次无工具生成调用，同日自动尝试上限按上文，不开启 19 工具循环。连接/响应/流空闲超时沿用网关并明确分层，单作业主动上限建议 240 秒；有持续流不按总字数过早截断，无进展则失败保留事实版。实际 usage 有则记录，无则未知，不承诺费用。

### 3.4 公告筛选、覆盖与短期存储

- “昨天”为上一北京自然日的发布时间，不是第一次抓到的日期；置顶和重复 URL/来源键去重。日期不明的不计入昨日条数，保留覆盖提示。
- 先取列表元数据，再按必要性读取有界正文片段；不下载附件、做 OCR 或把通知全文纳入知识库。财务关键词/FAQ 不可用不影响固定通知栏目。
- 初始预算：每来源最多 5 页、每页 20 项；最多读取 6 篇正文并控制片段总量，整个网络作业最多 20 请求（含重定向/直连复验），主动网络时间上限 60 秒。仅在已验证排序/边界下提前停止；否则标覆盖不足，不把预算结束说成“昨天没有通知”。
- 流程遵循原受控 HTTP、代理和校园 IP 直连策略，不改全局代理/TLS；登录才可读的内容继续跳过。无结果、失败、日期未知和部分覆盖分别呈现。
- 晨报结果/必要公告安全片段单独短期保存，建议 30 天、总量 5 MiB；不进入长期知识库、全文索引或主聊天。原始 HTML、学校认证响应、备注/任务正文、图片、音频与秘密不入事实包或缓存。
- 今日事实卡按业务变更刷新。生成时绑定今日输入摘要；关键安排改变后，旧生成结果不得作为当前版本落库或更新界面，保留基础卡并允许重新生成，不因每次编辑自动连续消耗模型额度。
- 用户主动“继续聊这份晨报”时，将日期、已允许摘要及受控出处作为当前讨论材料交给主 Agent，不自动合并全部晨报历史。

## 4. 系统提醒：业务期望与 OS 队列对账

### 4.1 规则与数据归属

- 两个提醒槽位分别可关闭/选择提前量。定时控件提供开始时、5/10/15/30/60 分钟、1 天及有界自定义；全天控件用日期/时间选择器，无手写格式。
- 全局默认与逐对象覆盖分开。重复个人日程支持“整个系列/仅本次”；单次覆盖按稳定 occurrence ordinal 绑定，来源同步、改期、重启不覆盖用户设置。
- 提醒设置是本地业务，不写学校；M5 现有工具修改时间、状态、出勤、任务或撤销时，C3 自动同步提醒期望。本期不增加模型自主修改提醒设置的工具或隐式新许可。
- 两槽同一时刻合并为一次有效系统提醒，界面仍保留两槽配置；已过提醒时刻不在启动时集中补弹。

### 4.2 同事务期望、事务外发布

在来源导入、本地/Agent 写、单次例外、状态变化和撤销的**同一 C3 事务**中持久化提醒期望：已展开目标的期望项，或足以确定其期望的目标身份、版本化规则及时间事实，并保存明确的撤销依据/outbox。删除、关闭、改期亦保留可恢复的旧逻辑键和当前期望版本；不能只写无版本 dirty 布尔值或只监听 UI 保存按钮，再依赖后续回调补建唯一事实。

通知逻辑键以 owner/reset、对象身份、occurrence、槽位为基础，版本/内容摘要用于对账而不直接制造第二个逻辑提醒。原生短 ID 通过持久映射产生，不直接塞数据库复合键。

应用组合层协调器依据 C3 的当前持久期望展开有界计划，P 在事务外登记/替换/撤销，再保存实际接受证据；平台失败不回滚已成功日程。崩溃在 OS 成功而 C3 尚未记账之间时，启动通过稳定键和原生枚举恢复，不重复登记。发布返回后同时复验 owner/reset epoch、当前期望版本和启用/关闭状态；普通编辑也能使旧版本失效。过时结果补偿撤销，失败留待办。

需要分别表示“业务已保存”“OS 已接受登记”“用户实际看到”。不能把平台调用 Future 返回或队列项消失当作已送达，也不承诺 exactly-once。

### 4.3 Windows 路线与前置验证

推荐先在现有 C++ runner 的 P 层做薄适配，使用 WinRT `ScheduledToastNotification` / `AddToSchedule`、计划枚举/撤销及受控激活。它利用 Windows 托管既已登记计划，不依赖 Dart Timer 或托盘进程。

当前 exe 要补齐稳定 AUMID/CLSID、用户级登记/快捷方式及退出后激活。只管理本应用身份，不写通知内部开关、不更改系统安全策略/证书信任，不读取其他应用通知；注册资产、开发/正式身份及路径变化有明确归属和清理方式。正常退出释放进程资源，**保留已登记未来提醒与必要冷启动注册**，不等同于关闭提醒。

开源插件 `flutter_local_notifications_windows` 3.1.1 有无包身份兼容、完整队列读回及冷激活细节需验证，不能只依据 README 推断“必须 MSIX”，也不能只依据 `schedule` 存在宣称可用。微软 Toolkit 的兼容源码作为注册/首发行为参考，不引入 C# 常驻辅助进程。

**最先做 M6.0 有限平台验证**：全新测试身份的第一个操作就是计划未来通知，然后彻底退出；验证出现、改期/取消、重复对账及点击冷启动。不能先手工显示一条通知后掩盖首次计划的缺口。若普通 exe 路线不能以小适配完成可靠撤销/冷激活，再提供 MSIX＋插件的具体发布取舍请用户决定，不静默更换安装/签名和数据位置。

### 4.4 覆盖、点击与系统限制

- 有限一次性/学校事件按已知未来时间展开；无限重复事件需有限规划。首版建议最多规划未来 180 天、512 条待发项，按最近提醒优先；这是应用保护预算，不冒充 OS 容量。显示实际已登记覆盖及待办，再次使用时延展。
- 超出容量/查询截断的区间不标全部成功；只按完整计算的范围替换/取消，不把未读到的事件当删除。完全退出后只能投递已交给 OS 的计划，不会无限扩展重复系列或生成新日程提醒。
- Windows 当前文档说明计划通知有 5 分钟投递窗口，关机错过过久可能丢弃。退出应用、Windows 重启/重新登录、睡眠/唤醒、关机错过、勿扰分别验证/说明；不保证关机时提醒、唤醒机器或突破用户系统开关。
- 默认系统内容只含日程名称、时间、地点和必要状态；可选隐私显示。无备注/任务正文、账号、认证资产或模型内容，用户能在系统设置控制横幅/锁屏。
- 点击只导航到当前对应日程/任务；已删除、reset、过时或伪造参数稳定拒绝/提示，不恢复旧写或 Agent 批准。已运行时激活同一实例，完全退出时冷启动；第二实例不得打开业务库写入。

## 5. 内部接口草案与失效

实现前在 M6.1 冻结字段/错误语义，下面是职责边界，不提前锁定类名或逐行代码。

| 契约 | 责任与不变量 |
|---|---|
| C0/C3 `ReminderPair` / `ReminderOverride` | 两槽、定时/日期型规则、继承/系列/单次作用域，按实际对象/版本保存；仅本地覆盖 |
| C3 `DesiredReminder` / outbox / native 映射 | 稳定逻辑键、UTC 时刻、内容摘要、目标世代、期望/接受/待撤销状态；与业务同事务；对账与事件版本分离 |
| P `NotificationPlatformPort` | 能力/用户开关、受控登记/枚举/替换/撤销、自己的已展示项清理及激活；返回时间/摘要等足够读回信息和稳定失败码，不把插件整数 ID 当业务身份 |
| C5/应用组合层 `ReminderCoordinator` | 编排 C3 持久期望与 P 发布/撤销，负责启动/变更/维护、受控补偿与重试；业务规则仍在 C3，P 不判业务；本地作业不占 C2 学校网络租约，正常退出不取消未来提醒 |
| C3 `MorningBrief` / ticket | 日键、日期窗口、阶段、来源覆盖、必要事实/摘要、输入摘要与 epoch、尝试和 usage；同日单飞、重启去重、过期拒交付 |
| C2 公告窗口查询 | 复用已登记两来源，日期归一化、去重、边界/预算和覆盖；不持有过期内存 cursor 跨重启恢复 |
| C4 模型作业仲裁/晨报摘要 | 前台优先、独立取消、当前模型/Key 租约与自动晨报同意；只读事实包、无工具、不污染主聊天 |
| C5 | 紧凑晨报卡、两槽编辑、开关/覆盖/测试通知与必要错误入口；不改变两个主页和日程大画布 |

schema 15→16 增量增加上述事实与设置，保留已有来源、个人安排/备注、任务/时间块、知识、模型/学校凭据、历史、许可和显示设置；迁移内不调用模型/学校/OS，不因添加功能自动开启出站或系统提醒。默认提醒可继承，不为每个旧事件制造无意义显式覆盖。冻结契约见[09 K-09](../../architecture/09-contracts.md#k-09-晨报与本地提醒)，组件/运行/隐私分别见10–12。

| 操作 | 晨报/提醒收口与保留 |
|---|---|
| 普通退出 | 停止/排空晨报与在途发布，保留已登记 OS 计划和短期结果 |
| 关闭晨报/撤回模型同意或删 Key | 立即停止相关请求；保留允许的本地资料；不再自动发模型 |
| 关闭系统提醒 | 停新发布、撤销自己的待发项及按确认范围清已展示项；取消失败保留明确待办，不更改日程 |
| 单独清晨报 | 作废 brief epoch 并排空，只清晨报；当天不自动重建，主动重试/次日再按规则处理 |
| 清聊天/清学校登录资料 | 不顺带删业务、提醒设置或晨报；沿用原维护范围并更新说明 |
| 清日程业务 | 停发/排空、撤销相关 OS 提醒，清除含对应业务的派生晨报；迟到结果不能恢复它们，凭据等仍按原范围保留 |
| 完全重置 | 持久屏障/epoch、排空全部作业、清本应用提醒及相关映射/晨报；OS 清理失败保持恢复待办，不假报全部完成 |

## 7. 验收条件

| 场景 | 必须成立 |
|---|---|
| 05:59/06:00、前台恢复/切页/同日重启/隔日 | 正确日键，最多一个同日活动作业，不混日期、不补多天、不重复卡片；受控再试计入同日上限，不无界重发 |
| 断网、无 Key、未同意、慢 SSE、主动聊天 | 基础卡可用，页面/日程/输入不被晨报锁住；服务器持续挂起/取消回调迟到时主动聊天仍在本地短上界内让路，取消只作用于本作业；失败保留已有内容 |
| 昨日无公告/源失败/未知日期/置顶重复/分页超限 | 空与失败/部分分别显示，来源、发布时间与读取时间可区分，未抓到不能说不存在 |
| 生成中编辑今日安排/清晨报/清业务/reset/改配置 | 旧结果拒交付，正确维护范围，不重建已清资产，不自动连续重生成 |
| 两槽、相同时刻、全天、系列/单次、任务/块 | 对象与时间准确；两槽同刻不双弹，独立状态不串改；每个未来 occurrence 的规则有效 |
| 同步/手工/Agent/撤销、缺失/隐藏/不参加 | 同一 C3 规则与期望账本；不丢本地覆盖，不因来源未观察就停提醒 |
| OS 成功/C3 记账前崩溃、改期、删除、迟到发布 | 重启可读回对账，无旧/重复计划；故障不反转已保存业务，撤销失败可恢复 |
| 全新通知身份、运行中/完全退出、Windows 重启/重新登录 | 各自记录实证，不能用应用重启代替系统重启，不能用先 show 后 schedule 掩盖首次问题 |
| 点击/冷启动/旧目标/reset、通知关闭/勿扰/关机错过 | 当前导航与实例正确，零旧写；尊重系统状态，区分接受/看到/错过，不提供虚假保证 |
| 保留、资源与安全诊断 | 合成旧库/回滚验证；维护及取消排空；日志只含固定阶段/码、数量、耗时/usage等安全元数据，不记录正文、日程、触发时间原值或激活令牌 |

自动检查仍仅用合成/loopback/临时资产；原生通知测试用独立身份和“测试日程”，不读取正式业务、学校会话、真实音频/秘密或调用真实模型/学校。不得改系统时钟、全局通知/勿扰或 TLS 设置来制造通过；需要 Windows 重启时由用户在方便时执行。

最终真人只集中核对：一次真实晨报（等待时能照常聊天/看日程）、一次两槽/改期、一次退出后的提醒及点击重开。Windows 重启持续性与系统抑制场景单列实证，未观察保留，不把机械 API 成功当用户已经看到。模型内容不要求用户贴回私人原文，可导出既有安全日志反馈失败。

## 8. 研究依据与适配判断

以下核对日期为 2026-10-15；支持的是文档/源码能力，不是本机功能已通过。

- [Microsoft 异步请求/响应模式](https://learn.microsoft.com/en-us/azure/architecture/patterns/asynchronous-request-reply)、[保持 UI 响应](https://learn.microsoft.com/en-us/windows/apps/develop/performance/keep-ui-thread-responsive)：借鉴任务/结果解耦，本项目使用现有本地协调器，不因此引入 Azure、消息服务器或新后端。
- [TanStack 缓存/后台重新验证](https://tanstack.com/router/latest/docs/guide/data-loading)：借鉴缓存、同键共享进行中结果和后台刷新；不为 Flutter 引入该 JS 库，也不把过日旧晨报伪装成今天。
- [Microsoft 计划通知](https://learn.microsoft.com/en-us/windows/apps/develop/notifications/app-notifications/app-notifications-scheduled)：OS 可在 app 不运行时投递、可枚举撤销，存在 5 分钟窗口；是选择系统调度而非进程 Timer 的依据。
- [Windows CommunityToolkit 身份/激活兼容源码](https://raw.githubusercontent.com/CommunityToolkit/WindowsCommunityToolkit/main/Microsoft.Toolkit.Uwp.Notifications/Toasts/Compat/ToastNotificationManagerCompat.cs)：作为普通 exe 登记、首次计划及冷激活的参考，M6.0 需当前系统实证，不照抄内部通知开关或另装 C# 常驻程序。
- [`flutter_local_notifications_windows` 3.1.1](https://pub.dev/packages/flutter_local_notifications_windows)、[固定版本调度/取消源码](https://raw.githubusercontent.com/MaikuB/flutter_local_notifications/flutter_local_notifications_windows-v3.1.1/flutter_local_notifications_windows/src/ffi_api.cpp)：成熟跨平台项目的对照；README 与待发项原生实现的能力表述有差异，需逐项核验，未因此锁定依赖或 MSIX。
- [Apple 本地通知](https://developer.apple.com/library/archive/documentation/NetworkingInternet/Conceptual/RemoteNotificationsPG/SchedulingandHandlingLocalNotifications.html)、[Android 闹钟](https://developer.android.com/develop/background-work/services/alarms)：未来端分别验证授权、调度、重启、撤销及系统限制，不能由 Flutter 同名 API 或 Windows 通过推断等价。

## 9. 批准后的阶段边界

M6 定为“可用晨报＋可靠的 Windows 日程提醒”，分切片推进，不单独扩大为后台同步或移动端阶段。批准范围包括：公告含教务与财务；任务截止纳入提醒、无截止不猜；全天采用当天 09:00 的明确例外；自动晨报/系统提醒分别一次启用；普通 exe 原生路线先行验证，发行/签名变化另作具体决定。

平台路线确定为普通 EXE、WinRT 调度及受控私有协议冷激活；首次身份的静默建立在明确启用后进行，不更换发行/签名。失败的冷COM路径及真实 API/进程证据见[01](records/01-windows-platform.md)。数据/UI、晨报及集成见[02](records/02-integration.md)。批准本身不等于真实晨报或实际 Toast 点击验收；M6 尚未关闭。
