## 1. 原关系语句（2026 春 电路/量子 二选一）

**目的：** 复测“2019 春”历史遗漏——两个历史课程重叠时，用户给出具体选择后应保存
`no_conflict`，而不是存成带 prose 的 `conflict`。

**给 Agent 的消息：**

> 找到 2026 春的“电路基本理论”和“量子物理 B”，把 2026 年 3 月 3 日那两节课记录为冲突，
> 我选择去量子物理 B。

**预期结果：**

- Agent 用有界的标题/日期查询定位这两个历史事件（不先整学期 `get_schedule` 长时间等待，
  也不无限“查引用”）。
- 给出具体选择后，关系以 `no_conflict` 保存（并存共存策略，不自动改出勤/听讲 overlay）。
- 确认卡只显示安全标题/时间，无 DB id / `ref_*`。
- 该 pairs 不再出现在冲突查询中；整段操作不依赖当前默认学期。

完成：1

## 2. 课程内部 PlanBlock 显式 no_conflict

**目的：** 验证混合关系（课程 CalendarEvent 与 Task 的 PlanBlock 重叠）可从重叠 UI 分类。

**操作步骤：**

1. 在一节已有课程的时间段内安排一个 Task 的执行时间段（PlanBlock）并确认。
2. 打开对应周，通过重叠展开进入“处理重叠关系”。
3. 把课程与 PlanBlock 的关系保存为“不冲突”。

**预期结果：**

- 课程与 PlanBlock 重叠时默认都显示红色圆圈冲突警告，重叠展开可进入关系编辑器。
- 保存 `no_conflict` 后两者仍都可见，但冲突警告消失；冲突查询不再列出该 pair。
- PlanBlock 分类不提供“优先显示”前景单选（无伪造 series 身份）。

完成：1

## 3. 六秒本地撤销提示（不遮挡聊天）

**目的：** 验证整日移动后的撤销提示是日程页本地浮动条，六秒消失，不盖住聊天。

**操作步骤：**

1. 在日程页对日期 A 执行整日移动（移动教务课程到 B）并确认。
2. 观察更新提示是否出现在日程页底部、是否离开日程页（切到聊天）后立即消失。
3. 大约 6 秒后确认提示自行消失；期间点击“撤销”恢复。

**预期结果：**

- 提示是 `schedule-undo-notice` 本地浮动条，**不是**全局 SnackBar，切页即消失。
- 大约恰好六秒后消失（无论是否已导航）。
- 六秒内点“撤销”一次恢复移动，恢复后提示消失。
- 提示从不出现在聊天页，不遮挡聊天输入。

完成：1

## 4. Agent 整日移动的终态结果

**目的：** 复测确认后的 Agent 整日移动必须以成功终态结束，不再出现尾随 `grounding_failed`。

**给 Agent 的消息：**

> 把 A 这一天的所有教务课程移动到 B，其他日程不要动。

将消息中的 A、B 替换为第 0 节记录的真实日期。

**预期结果：**

- 点击确认后移动成功写入，聊天最终回复总结移动结果，**不以** `grounding_failed` 结尾，
  也无“请你重试”之类的伪失败话术。
- 非教务日历（考试、二课、个人事件、PlanBlock）不随之移动；若 A 当天没有某类数据，在
  记录中注明“无样本”。
- 取消时不移动且只能报告取消；源事件未被物理改写。
- 测试结束后清除该移动。

完成：1

2. 重启 App，回到同一账号，找到该轮对话并展开工具过程。

**预期结果：**

- 账号乙看不到账号甲的任何工具诊断记录。

## 6. 学期 Task 请求先摘要再澄清

**目的：** 验证“这学期有哪些作业/任务”之类的请求用 `course_summary` 摘要，先问未决细节，
并保留可多次 `create_task` 的既有能力。

**给 Agent 的消息：**

> 这学期我有哪些课程作业要完成？

再根据其回答追问细节，例如：

> 给“电磁场与波每周六作业”建立任务，每周六截止。

**预期结果：**

- Agent 先尝试 `course_summary`（或窄范围）读取，而不是先做整学期 `events` 大范围读取并
  长时间等待/失败（较大范围详细 `events` 请求应被 `schedule_summary_required` 引导回摘要）。
- 对未决的作业细节（标题、截止、频率）先向用户澄清，不再静默假设。
- 澄清后仍可多次 `create_task`（如多门课各建一个），批量能力不被破坏。
- 不依赖当前默认学期，无硬编码 semesterId 进入请求。

## 10. 单日确定已有任务的关系安排（2026-08-03 修复后验收）

**测试目的：** 复测原始故障。用户用日期+节次（不含课程标题）指明关系参与方，并要求
把已有任务安排进这个时间段、标记为不冲突。验证 Agent 通过同一日的
`get_schedule(view=events)` 按时间定位第一节课程，不猜测课程名，并顺序完成
PlanBlock 与 Relation 两个写流程。

**给 Agent 发送（原文，不可改动）：**

> 在9月1号上午第一节课我想再写一门生命科学简史课作业，你只要帮我安排在这个时间段，
> 具体事件我自己把握，并标记为不冲突。

**操作前置：** 在当前账号保留名为“生命科学简史课作业”的已有 Task，并在本地日程中保留
2026 年 9 月 1 日当天至少三个课程事件（第一节 07:50-09:25、第二节 09:45-11:20、下午
15:55-17:30），其中第一节的“计算机网络”为第一节事件。

**操作步骤：**

1. 发送上述原始句子，展开本轮“工具调用”，记录工具名、调用次数和错误码。
2. 观察第一张写确认卡：确认操作标签为“安排任务时间段”、目标为已有 Task
   “生命科学简史课作业”且时间段为 07:50-09:25，然后点击确认。
3. 观察第二张写确认卡：确认操作标签为“记录日程关系”，两侧为“计算机网络”与对应
   执行块、关系为“不冲突”，确认卡不显示内部 ID 或 `ref_*` 原值，然后点击确认。
4. 打开 2026 年 9 月 1 日所在周，确认日程页同时显示该课程与 PlanBlock，且两者重叠
   但红色冲突警告消失。
5. 点击课程确认进入课程详情、点击执行块确认进入所属 Task 详情，二者未被混淆。

**预期结果：**

- Agent 先以 `get_tasks` 取得已有“生命科学简史课作业”，并以
  `get_schedule(from=2026-09-01, through=2026-09-01, view=events)` 取得当天三个事件引用；
  调用 `get_schedule` 不携带课程标题 `query`，也不会向用户追问或猜测“计算机网络”。
- 第一节课程由返回的开始/结束时间（07:50-09:25）唯一确定。
- 五工具顺序执行且各有一次成功：`get_tasks -> get_schedule -> plan_task ->
  get_plan_blocks -> create_schedule_relation`；`get_plan_blocks` 使用本轮 `get_tasks`
  返回的任务引用取得新 PlanBlock 引用后，`create_schedule_relation` 才能执行。
- 出现两张顺序确认卡：第一张为 PlanBlock（安排任务时间段），第二张为 Relation
  （记录日程关系），二者各自等待用户批准。
- 全部批准后，只生成一个 PlanBlock 和一条 canonical Relation
  （event↔PlanBlock、`no_conflict`）；两事件/块仍按原时间重叠显示，但冲突警告消失。
- 本轮不出现 `relation_lookup_requires_title`、`relation_lookup_requires_bound`、
  重复调用风暴或尾随 `protocol_error`。
- 如果数据库已有同名课程或相关关系，本次更新同一行，不产生重复 PlanBlock 或重复关系。

**第一次确认取消检查：** 在“安排任务时间段”确认卡点击取消——不创建 PlanBlock，也不再
执行 `create_schedule_relation`；最终回复不得声称已写入，也不得出现“没有修改数据”之外的
虚假成功。

**第二次确认取消检查：** 批准 PlanBlock 后，在“记录日程关系”确认卡点击取消——保留已创建的
PlanBlock，明确报告“执行时间段已创建，但不冲突关系未保存”（不得笼统报告“没有修改数据”）。

**失败记录至少包含：**

- 发送给 Agent 的原始自然语言消息。
- 出错前后的操作步骤。
- 工具名称、调用次数、可见状态和安全错误码（尤其是 `plan_task` 与
  `create_schedule_relation` 的状态）。
- 页面实际表现与预期表现（确认卡、重叠警告、详情入口）。
- 是否重启可复现，但不要记录任何密钥、学号、内部数据库 ID 或 `ref_*` 原值。
