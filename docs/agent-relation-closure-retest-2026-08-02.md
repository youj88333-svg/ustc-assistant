## 1. 历史课程二选一保存为“不冲突”

**测试目的：** 复测原始故障。用户已经作出取舍时，即使话语中包含“冲突”，最终关系也应
是“不冲突”，而不是只把选择写进冲突原因。

**给 Agent 发送：**

> 找到 2026 春的“电路基本理论”和“量子物理 B”，把 2026 年 6 月 2 日那两节课记录为冲突，
> 我选择去量子物理 B。

**操作步骤：**

1. 展开本轮“工具调用”，记录工具名、调用次数和错误码。
2. 出现写确认卡时，确认关系显示为“不冲突”，然后点击确认。
3. 打开 2026 年 6 月 2 日所在周，点击这两个重叠课程并进入关系管理。
4. 再次向 Agent 查询这一天的冲突关系。

**预期结果：**

- Agent 以课程名和具体日期做有限查询，不先扫描整学期的详细课次。
- 写确认卡显示“不冲突”，不显示内部 ID 或原始引用。
- 两门课都保留在原时间；系统不自动修改出勤或听讲状态。
- 两门课的红色冲突警告消失，并且不再出现在冲突查询结果中。
- 如果数据库里已有之前误建的 `conflict` 关系，本次应更新同一关系，不产生重复关系。
- 即使当前默认学期不是 2026 春，本次查询和修改仍可完成。

完成：正常

## 2. 课程与 PlanBlock 的混合重叠关系

**测试目的：** 验证课程中安排其他任务时，课程与 PlanBlock 能被显式标记为“不冲突”。

**操作步骤：**

1. 新建 Task：`[验收] 课程内作业 A`。
2. 为该 Task 安排一个与某节课程明显重叠的 PlanBlock，并接受该规划。
3. 打开对应周，第一次点击重叠区域，确认会单独展开重叠安排。
4. 分别点击课程和 PlanBlock，确认课程进入课程详情，PlanBlock 进入所属 Task 详情。
5. 再次展开重叠区域，点击“处理重叠关系”。
6. 将课程与 PlanBlock 的关系改为“不冲突”，填写可辨认的测试原因并保存。

**预期结果：**

- 未分类时，两项都可见并显示红色圆圈感叹号。
- 关系编辑页同时正确显示课程标题与 Task/PlanBlock 标题。
- 只要一侧是 PlanBlock，“应用到当前及未来兼容课次”就处于禁用状态。
- 保存后两项仍按原时间重叠显示，但红色冲突警告消失。
- 两项各自的详情入口仍然正确，没有把 PlanBlock 当成课程事件。

完成：正常

## 3. PlanBlock 与 PlanBlock 及三项重叠

**测试目的：** 补测统一关系模型的第三类组合，并验证三项重叠会生成全部无序 pair。

**操作步骤：**

1. 在第 2 项同一时间段再创建 Task：`[验收] 课程内作业 B`。
2. 为 Task B 安排并接受一个与课程、PlanBlock A 都重叠的 PlanBlock。
3. 点击重叠区域，再进入“处理重叠关系”。
4. 确认页面列出三对关系：课程/A、课程/B、A/B。
5. 把 A/B 标为“不冲突”，保存后重新打开关系管理页检查状态。

**预期结果：**

- 三个安排都能在重叠展开中看到，且每个都能点击进入正确详情。
- 三项只生成 3 对关系，不缺失也不重复。
- PlanBlock/PlanBlock 关系只能作用于本次，不能应用到当前及未来。
- 反复保存或交换选择顺序不会产生第二条反向重复关系。
- 保存 `no_conflict` 后 A/B 的冲突警告消失，其他未分类 pair 的警告仍按各自状态显示。

## 4. 日程页六秒撤销提示

**测试目的：** 验证整日调课后的提示只属于日程页，不遮挡聊天，并保持一步撤回能力。

**操作步骤：**

1. 在日程页点击“整日调课”，把日期 A 的所有教务课程移动到日期 B。
2. 操作成功后观察日程页底部提示，等待约 6 秒。
3. 再执行一次移动，在 6 秒内切换到聊天页。
4. 返回日程页重新执行移动，并在 6 秒内点击“撤销”。

**预期结果：**

- 成功后出现带“撤销”按钮的日程页局部提示。
- 提示约 6 秒后自动消失；消失不等于删除数据库里的一步撤回记录。
- 切到聊天页时提示立即消失，聊天输入框不被遮挡。
- 6 秒内点击“撤销”只执行一次，课程恢复到移动前日期，提示随即消失。
- 考试、二课、个人事件和 PlanBlock 均未随整日教务课程移动。

## 5. Agent 整日移动成功终态

**测试目的：** 验证确认后的成功写入不会再被尾随的 `grounding_failed` 覆盖。

**给 Agent 发送：**

> 把 A 这一天的所有教务课程移动到 B，其他日程不要动。

发送前请把 A、B 替换为第 0 项记录的实际日期。

**操作步骤：**

1. 检查确认卡中的源日期、目标日期和课程数量，然后点击确认。
2. 等待本轮 Agent 完整结束，展开工具调用。
3. 在日程页检查 A、B 两天；随后通过整日调课界面清除本次移动。
4. 再发起一次移动，但在确认卡点击取消。

**预期结果：**

- 确认后只产生一次有效整日移动，最终回复明确报告成功。
- 本轮不以 `grounding_failed`、伪失败或“请重试”结尾。
- 工具调用显示 `move_jw_course_day` 成功，操作历史只记录安全摘要。
- 取消确认时不修改日程，Agent 只能报告取消，不能声称已完成。
- 整日移动只作用于课程类型的 `ustc_jw` 事件。

## 6. 工具调用生命周期、重启恢复与隐私

**测试目的：** 验证运行中和重启后的工具诊断一致，并且不会泄露敏感字段。

**操作步骤：**

1. 让 Agent 查询一个具体日期的课表，等待成功。
2. 让 Agent 新建一个测试 Task，在确认卡出现时先观察工具状态，再点击取消。
3. 展开两轮“工具调用”，记录工具名、状态、错误码和耗时是否合理。
4. 完全退出并重新启动 App，回到同一账号，再展开刚才两轮工具调用。
5. 如有第二个测试账号，切换账号确认看不到第一个账号的调用记录。

**预期结果：**

- 写工具等待确认时显示等待状态；取消后变为取消状态，而不是永久停留在运行中。
- 成功、失败、取消等状态与本轮真实结果一致。
- 重启后工具名、调用次数、状态、安全错误码和耗时仍可查看。
- 展开内容不含 API Key、Cookie、Token、完整学号、数据库 ID、`ref_*` 原值或完整课表。
- 不同学校账号的聊天和工具诊断相互隔离。

## 7. 学期摘要优先与周期 Task 澄清

**测试目的：** 验证学期级请求不会先读取超大范围详细课次，并保留多次
`create_task` 的实现方式。

**给 Agent 发送：**

> 我下学期电磁场与波这门课的作业每周六交，请给我每周六设置一个 Task。

**操作步骤：**

1. 观察 Agent 首轮回复和工具调用，但先不要确认任何写操作。
2. 根据 Agent 的问题补充课程范围、第一次和最后一次截止日期、Task 标题规则等信息。
3. 为避免重复污染数据，建议本轮只确认两个连续周六作为抽样；若要完整验收，可确认整个
   有效课程范围。
4. 检查确认卡数量和最终创建结果，测试后删除 `[验收]` Task。

**预期结果：**

- Agent 先使用 `get_schedule(view=course_summary)` 或等价窄范围摘要，不先读取整学期
  `events`。
- 不出现首次大范围查询失败后才改用摘要的多余流程。
- 日期范围、截止时间或特殊周次不明确时，Agent 先询问，不静默猜测。
- 用户明确范围后，Agent 可多次调用现有 `create_task`，每个周六建立独立 Task。
- 不创建 TaskSeries，不把所有周次合并成一个不可独立完成的 Task。
- 最终回复准确区分成功、取消与失败的项目，不虚报全部成功。
- 请求不依赖硬编码的 `semesterId`；切换默认学期后仍以用户指定的学期和同步数据为准。

## 10. 单日确定已有任务的关系安排（2026-08-03 修复后验收）

**测试目的：** 复测原始故障。用户用日期+节次（不含课程标题）指明关系参与方，并要求
把已有任务安排进这个时间段、标记为不冲突。验证 Agent 通过同一日的
`get_schedule(view=events)` 按时间定位第一节课程，不猜测课程名，并顺序完成
PlanBlock 与 Relation 两个写流程。

**给 Agent 发送（原文，不可改动）：**

> 在9月1号上午第一节课我想再写一门生命科学简史课作业，你只要帮我安排在这个时间段，
> 具体事件我自己把握，并标记为不冲突。

**操作前置：** 在当前账号保留名为“生命科学简史课作业”的已有 Task，并在本地日程中保留
2026 年 9 月 1 日当天至少三个课程事件（第一节 07:50-09:25、第二节 09:45-11:20、下午
15:55-17:30），其中第一节的“计算机网络”为第一节事件。

**操作步骤：**

1. 发送上述原始句子，展开本轮“工具调用”，记录工具名、调用次数和错误码。
2. 观察第一张写确认卡：确认操作标签为“安排任务时间段”、目标为已有 Task
   “生命科学简史课作业”且时间段为 07:50-09:25，然后点击确认。
3. 观察第二张写确认卡：确认操作标签为“记录日程关系”，两侧为“计算机网络”与对应
   执行块、关系为“不冲突”，确认卡不显示内部 ID 或 `ref_*` 原值，然后点击确认。
4. 打开 2026 年 9 月 1 日所在周，确认日程页同时显示该课程与 PlanBlock，且两者重叠
   但红色冲突警告消失。
5. 点击课程确认进入课程详情、点击执行块确认进入所属 Task 详情，二者未被混淆。

**预期结果：**

- Agent 先以 `get_tasks` 取得已有“生命科学简史课作业”，并以
  `get_schedule(from=2026-09-01, through=2026-09-01, view=events)` 取得当天三个事件引用；
  调用 `get_schedule` 不携带课程标题 `query`，也不会向用户追问或猜测“计算机网络”。
- 第一节课程由返回的开始/结束时间（07:50-09:25）唯一确定。
- 五工具顺序执行且各有一次成功：`get_tasks -> get_schedule -> plan_task ->
  get_plan_blocks -> create_schedule_relation`；`get_plan_blocks` 使用本轮 `get_tasks`
  返回的任务引用取得新 PlanBlock 引用后，`create_schedule_relation` 才能执行。
- 出现两张顺序确认卡：第一张为 PlanBlock（安排任务时间段），第二张为 Relation
  （记录日程关系），二者各自等待用户批准。
- 全部批准后，只生成一个 PlanBlock 和一条 canonical Relation
  （event↔PlanBlock、`no_conflict`）；两事件/块仍按原时间重叠显示，但冲突警告消失。
- 本轮不出现 `relation_lookup_requires_title`、`relation_lookup_requires_bound`、
  重复调用风暴或尾随 `protocol_error`。
- 如果数据库已有同名课程或相关关系，本次更新同一行，不产生重复 PlanBlock 或重复关系。

**第一次确认取消检查：** 在“安排任务时间段”确认卡点击取消——不创建 PlanBlock，也不再
执行 `create_schedule_relation`；最终回复不得声称已写入，也不得出现“没有修改数据”之外的
虚假成功。

**第二次确认取消检查：** 批准 PlanBlock 后，在“记录日程关系”确认卡点击取消——保留已创建的
PlanBlock，明确报告“执行时间段已创建，但不冲突关系未保存”（不得笼统报告“没有修改数据”）。

**失败记录至少包含：**

- 发送给 Agent 的原始自然语言消息。
- 出错前后的操作步骤。
- 工具名称、调用次数、可见状态和安全错误码（尤其是 `plan_task` 与
  `create_schedule_relation` 的状态）。
- 页面实际表现与预期表现（确认卡、重叠警告、详情入口）。
- 是否重启可复现，但不要记录任何密钥、学号、内部数据库 ID 或 `ref_*` 原值。
