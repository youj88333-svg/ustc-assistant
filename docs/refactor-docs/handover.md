## 4. 工作流程与纪律（本会话沉淀，照做）

1. **先自审再送审**：新产出先按本层 gate 逐条自审（本会话自审多轮抓出大量缺口），
   修补后再生成独立审查 prompt。
2. **审查 prompt 配方**（各层通用）：项目背景一句话 → 审查对象+参照物+阅读顺序
   → 本层 gate 判据 → 已知整改清单（供核验勿重复报）→ 必须执行的机械检查清单
   → 报告格式（总评/闭合核对表/问题分级 A/B/C/拍板项复核/gate 判定）→ 硬约束
   （只读、不跑测试、不访问学校网站、不重开已拍板项、中文）。
3. **审查报告处理**：先核实证据（不盲信）→ 分批次整改（机械类先行，契约缺口
   **回写对应层**并在该层 L 表登记）→ 触及已拍板项的结论**必须用户重审**。
4. **审查者直接改文件时**：主 agent 逐 diff 复审——核对与用户决断的冲突
   （技能 `receiving-code-review`：与既有拍板冲突先停下问用户）、代码事实、
   跨文档一致性；发现"用户批准"类标注必须与真实批准对上再提交。
5. **用户偏好**：拍板一项一项来；拍板前查成熟开源项目参考；技术细节用房子/
   餐馆等比喻；批准即落 ADR/L 表。
6. **机械纪律**：`git diff --check` 每提交必跑；旧表述残留用 grep 全库检索清零；
   数字（CT 数/L 编号/表数）跨文档一致后再提交。
7. **工具坑**：git 提交会触碰文件 mtime，`edit` 报 "file changed" 时先 re-read
   目标段再改。
8. **永不提交**：`.statusline-test/`、`_merge-pending-docs/`（用户目录）；
   `temp.md` 是 gitignored 私有速查。
9. **不得**：运行 Flutter/Python 测试或访问学校网站（设计阶段只改文档）；
   替用户改验收结论；把自动测试通过写成人工验收通过。
